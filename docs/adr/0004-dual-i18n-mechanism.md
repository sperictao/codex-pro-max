# 前后端双翻译机制：前端 i18next + Rust 极简字典

启动器多语言（见 CONTEXT.md "界面多语言"域）在前端用 i18next（英文原文作 key、扁平 JSON 资源、缺失兜底英文），Rust 侧另起一个极简 `i18n.rs`（`tr(lang, key)` + 两张 match 表，同 key 风格），托盘菜单、进程状态消息、invoke 错误串在产出处就地翻译，前后端 IPC 契约不变、前端照旧原样显示。

反直觉之处：明明前端已有 i18next，却让 Rust 再维护一套翻译机制，看似重复。原因是单一设施的替代方案要求 Rust 不再产出人话、约 35 个错误产出点加 `ProcInfo.message` 全部改为结构化错误码契约、前端 toast/状态渲染同步重写——为约 40 条字符串重构整条错误链路，churn 与收益不成比例；且前后端字符串本是不相交的两个集合，重复的只是约 50 行的机制而非数据。语言设置的单一事实来源仍在 Rust（`LauncherConfig.language` + 启动时 `sys-locale` 一次性解析），前端从 `load_config` 取解析结果，两套机制消费同一个解析语言，不会分叉。

**Considered Options**：错误码契约（Rust 只返 `{ code, params }`，i18next 统一翻译）——设施单一、加第三语言时扩展性更好，但重构面过大且契约改动波及所有错误处理路径；否决，若未来支持第三种语言再重新评估。**Consequences**：新增用户可见字符串时前后端要各自登记词典，没有跨进程的统一缺失扫描；切换语言即时生效（前端重渲染 + 托盘重建），但已产生/已显示的消息不回溯重翻。
